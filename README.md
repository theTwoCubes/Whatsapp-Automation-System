# WhatsApp Automation

A production WhatsApp lead nurturing platform built on the WhatsApp Cloud API.
Leads message the business and an AI answers from a curated knowledge base,
follow ups go out automatically on a schedule, and a team can take over,
accept, or hand back any conversation from a web console. The system is
white labelled and environment driven, so it can be pointed at a different
client account by changing configuration alone.

The platform is inbound first. A lead's message opens a 24 hour service
window, and free form replies are only sent inside that window. Once it
closes, only Meta approved message templates can be sent, which is how the
drip follow ups reach a lead afterward.

For deployment steps, see [DEPLOY.md](DEPLOY.md). For a checklist to set up
a new client, see [CLIENT_ONBOARDING.md](CLIENT_ONBOARDING.md).

## Capabilities

### Conversational AI

- Replies are generated by OpenAI or Google Gemini. One provider is primary
  and the other is used as automatic failover if the primary errors. If
  neither is configured, or both fail, the bot falls back to a canned
  message so a lead is never left without a reply.
- Every reply is grounded strictly in the configured business description
  and the knowledge base. The model is instructed not to invent prices,
  timelines, or policies that are not written down, and to say it will
  check rather than guess.
- The system prompt is hardened against prompt injection. Anything a lead
  sends is treated as a message to answer, never as an instruction, and the
  model is told to refuse attempts to reveal its instructions, change its
  role, or act outside the business's own services.
- Replies are written in a plain, human tone. Markdown formatting, bullet
  points, headings, and em dashes are stripped before a message is sent, so
  it reads like it was typed by a person on WhatsApp.
- The model also judges, on its own, when a conversation needs a human,
  independent of keyword matching, and gives a short reason when it does.

### Knowledge base

- Facts are stored in a tiered structure: a shared base layer available to
  every conversation, and per Topic packs for individual services or ad
  campaigns.
- Retrieval is pack based, not a similarity search: the base pack plus the
  lead's linked Topic (and any Topic its keywords match) are handed to the
  model close to verbatim, packed into a fixed token budget so prompts stay
  bounded. The model can also ask for one more Topic pack by name mid-reply
  if the current answers do not cover the question.
- Facts can be added one at a time, or pasted in bulk (an FAQ document, raw
  notes) and split automatically into atomic units. Deduplication is
  deliberately literal rather than similarity based: re-loading a pack
  replaces that pack's rows, so editing the source file always wins and
  repeated loads never leave duplicates behind.
- Facts can be edited, deactivated, or deleted from the console at any time
  without a deployment.

### Media library

- Media assets (images and documents) are uploaded through the console,
  tagged to a Topic, and given a short description of when the file
  applies.
- The descriptions for the conversation's Topics are handed to the model
  alongside the approved answers, and it names the file to attach as part
  of its decision. A file can also be pinned directly to one FAQ answer,
  so using that answer sends the file with it. A cooldown keeps the bot
  from repeatedly resending the same file to the same conversation without
  hard blocking a lead who genuinely asks again.
- Media a lead sends is never silently dropped. An inbound photo or PDF is
  read once with Gemini vision for a short, factual, non-judgemental
  description (never a critique or analysis of the file itself, which stays
  a paid, human step where that applies) - rate limited per conversation so
  it cannot be used to run up the vision bill. Sending a file is never, on
  its own, a reason to hand a conversation to a person.
- A human agent can also browse the library by Topic from the chat composer
  and send any file directly, independent of the bot.

### Payment links

- Like the media library, a payment link (label, amount, url, and a
  description the AI reads) can be attached to a Topic from the console.
  The AI offers the right one when the approved answers for that service
  call for it, and treats a lead's own "I've paid" as one signal toward
  qualifying them, not something it verifies against a payment provider.

### Message handling

- Rapid, successive messages from the same lead are coalesced into a single
  AI call and a single reply instead of one reply per message, using a
  short configurable debounce window with a hard maximum wait.
- Every inbound webhook delivery is deduplicated by message id, so a retry
  from Meta never produces a duplicate reply.

### Lead qualification and handoff

- The bot only hands a conversation to a person once the lead is actually
  qualified: what their business is, where they are based, and what they
  specifically want, plus an email or an explicit "I don't have one" -
  not just because it is unsure of one fact, a price got pushed back on,
  or a file came in.
  Name, business, email, address, requirement, budget, and timeline are
  picked up conversationally as they come up and saved to the lead, visible
  in full on the console's chat sidebar and the dashboard's leads table.
- Pricing never negotiates. A discount request gets a firm, friendly answer
  and the conversation continues - it is never, on its own, a reason to
  hand off.
- A handoff is a two step process. Once the bot judges a lead is qualified,
  or a lead explicitly and sincerely asks for a person, the conversation
  moves to a pending queue with a short reason attached (summarising who
  they are and what they want), rather than jumping straight to looking
  like it is already being handled.
- Any agent can accept a pending handoff, or reject it - either way that
  agent becomes the conversation's owner, since accepting means "this
  needed a person, that's me" and rejecting means "the bot should not have
  flagged this, but I will deal with it myself" rather than send it back to
  the bot unowned.
- An agent can also take over a bot owned conversation directly at any
  time. Replying to any conversation that is not already an agent's own
  claims it automatically and stops any scheduled follow ups on it.
- A conversation nobody accepts or replies to within a configurable number
  of minutes is handed back to the bot automatically, and the bot answers
  the lead's waiting message so they are not left hanging.

### Follow up automation

- After a bot reply, a sequence of follow up messages can be scheduled
  using approved WhatsApp templates. The sequence ships empty, since the
  template names have to match templates actually approved in the client's
  WhatsApp Manager; it is configured per service from the console's
  Follow-ups page once they are synced. Every new reply from the lead
  resets the schedule.
- Follow ups are sent using row level locking, so running more than one
  instance of the scheduler never sends the same follow up twice.
- A handoff, whether initiated by the bot, the lead, or an agent, cancels
  any pending follow ups for that conversation.

### Campaign attribution

- Leads who arrive through a click to WhatsApp ad are automatically linked
  to the ad campaign that brought them in, captured from the referral data
  in the first message.
- A campaign can be linked to a knowledge Topic from the console, which
  biases the bot's answers for that campaign's leads toward the relevant
  service without excluding the shared knowledge base.
- The console reports lead counts, conversation state, and message volume
  broken down per campaign, with a separate bucket for organic leads that
  arrived with no ad referral.

### Continuous learning

- A scheduled weekly pass scans conversation transcripts for general,
  reusable facts a team member stated that are not already in the
  knowledge base, using a cursor so each run only looks at messages added
  since the last one.
- Anything found is queued inactive under its Topic rather than published
  automatically. It only reaches the bot once an agent reviews and approves
  it from the console, or rejects it.
- The pass can also be run on demand instead of waiting for the weekly
  schedule.

### Web console

- A live chat view lists every conversation with its state, sorted by
  recent activity. An unread badge tracks inbound messages that haven't
  been seen by an agent yet.
- The view updates in real time over a websocket as messages and status
  changes arrive. Message status is tracked with granular red/white ticks,
  matching WhatsApp's native blue tick read receipt behaviour. Messages
  sent by the AI also automatically mark the lead's previous inbound
  messages as read.
- Agents can send free form messages and media within the 24 hour window,
  or send an approved template at any time, including outside the window.
- An admin panel covers: an activity overview, campaign attribution,
  the WhatsApp business profile, the tiered knowledge base, the media
  library, message templates (including creating and submitting new ones
  for Meta approval), agent accounts, runtime settings, white label
  branding, and an audit log of console actions.

### Multi agent access

- Agents sign in with an email and password, authenticated with a signed
  token. Passwords are hashed with scrypt and a per password salt.
- Every action taken from the console (takeovers, handoff decisions,
  messages, settings changes, knowledge and media edits) is recorded in an
  audit log with the acting agent, the action, and its target.

### White label branding

- The console's display name, watermark text, support email, and accent
  colour are configurable from the console itself, with no redeploy
  required, so the same codebase can be reused across different client
  accounts.

### Security and reliability

- Inbound webhooks are verified against Meta's X-Hub-Signature-256 header
  using a constant time comparison before any payload is processed.
- The console API is rate limited, with a stricter limit on login attempts
  specifically, and every response carries standard security headers
  including a content security policy.
- Errors are logged in full on the server but never echoed back to a
  client, so internal details are never exposed through an API response.
- The process shuts down cleanly on an unexpected error rather than being
  left in a broken state, and the database migration runner is retried on
  boot to tolerate a database that is still starting up.
- The application container runs as a non root user and exposes a health
  check endpoint used by the orchestration layer.

## Architecture

Node.js with Fastify on the backend, PostgreSQL with the pgvector
extension for storage and vector search, and a React single page
application for the console. All outbound WhatsApp Cloud API calls go
through a single client module, so switching WhatsApp accounts is a matter
of changing configuration rather than code.

Background work (follow up delivery, auto resume, the weekly learning
pass) runs on a recurring in process interval rather than a separate
worker, since a single instance is sufficient at the scale this platform
targets.

## Requirements

- Node.js 20 or newer
- PostgreSQL with the pgvector extension
- A Meta app with the WhatsApp product enabled: a phone number id, a
  WhatsApp Business Account id, an access token, and the app secret
- An OpenAI API key, a Gemini API key, or both. Either one is enough to
  run the bot; configuring both buys automatic failover. A Gemini key is
  what reads an inbound photo or PDF, with OpenAI used only as the vision
  fallback, so set Gemini even if OpenAI is the primary chat provider
- A way to expose the local server to Meta during development, such as
  ngrok or cloudflared
- To compile the Android APK: the Android SDK and a Firebase project 
  (`google-services.json`) configured for Push Notifications.

## Setup

Install dependencies for both the server and the console:

    npm install
    cd web && npm install && cd ..

Copy the environment template and fill it in:

    cp .env.example .env

Every configurable value, its purpose, and its default is listed in
`.env.example`. Required variables are checked at boot; a missing one stops
the server with a message naming what is absent.

Run the database migrations:

    npm run migrate

## Running locally

Start the server:

    npm run dev

Build the console for the server to serve, or run its own dev server from
`web/` with `npm run dev` there:

    cd web && npm run build

Expose the server in a second terminal so Meta can reach the webhook:

    ngrok http 3000

### Configuring the webhook in Meta

1. In the Meta app dashboard, open WhatsApp, then Configuration.
2. Set the callback URL to `https://YOUR-URL/webhook`.
3. Set the verify token to the value of `WEBHOOK_VERIFY_TOKEN`.
4. Save. The verification handshake should pass.
5. Click Manage next to the webhook fields and enable the `messages`
   field. Without this the webhook verifies but never receives anything.

## Testing

The test suite runs against a throwaway PostgreSQL database and covers the
webhook flow, the console API, the knowledge and media pipelines, the
handoff lifecycle, the scheduler, and the learning pass:

    npm run qa

## Project layout

- `src/handlers` - inbound webhook processing and message batching
- `src/ai` - the AI client, provider adapters, embeddings, reply building,
  and output sanitisation
- `src/knowledge` - the knowledge base, media library, ingestion, dedup,
  retrieval, and weekly learning
- `src/routes` - the console API
- `src/db` - migrations and data access
- `src/meta` - the WhatsApp Cloud API client
- `web/` - the React console
- `qa/` - the test suite
