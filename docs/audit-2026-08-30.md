# Codebase audit — 2026-08-30

Scope: production-readiness pass across backend (Fastify + Postgres),
frontend (Vite/React), service worker, PWA manifest, Capacitor APK, and the
notification stack. Nothing has been changed here — this is only the
findings list for a later fix pass.

Severity legend used below:

- **P0** — visible bug, silent failure, or security concern.
- **P1** — likely to bite in real use; visible UX flaw; wrong-on-mobile.
- **P2** — nice-to-have polish; small dead code; docs drift.

Each finding names one file and one root cause. Where a punch-list item from
[production-punchlist.md](production-punchlist.md) covers the same ground,
that section is cited so you can hand a fresh agent both docs together.

---

## A. Backend and push delivery

### A1 · P0 · Push preview leaks the whole message body across the internet
**File:** [src/handlers/message.js](../src/handlers/message.js) around the
state-not-bot branch. The `preview` is `message.text.body.slice(0, 120)` and
becomes the notification body, which is delivered by Google/Apple/Mozilla push
servers as opaque encrypted payload — that's fine per WhatsApp guidelines, but
the same string ends up in the Android system notification tray, on the lock
screen, and in Firebase's server-side logs when the FCM path is used.

**Risk:** if a lead sends "Card number 4111 1111 1111 1111 expires 08/29 CVV
123", that goes to the lock screen. For AdVoice this is very unlikely but
worth being explicit about.

**Fix path:** either truncate to 40 chars, or replace preview entirely with
"New message" for non-handoff pushes.

### A2 · P0 · FCM path never actually delivers without google-services.json + service account
**File:** [src/push.js](../src/push.js) `notifyAgentsOfHandoff` FCM branch.

The code calls `getMessaging().send(...)` which throws
`FIREBASE_APP_ERROR` at runtime if the service account is missing. Currently:
- `configureFcm()` returns silently when `FCM_SERVICE_ACCOUNT_JSON` env var
  is empty.
- The push loop logs `"fcm not configured, skipping"` and moves on.

So there is no "notification not delivered" surface anywhere in the app —
the client sees nothing on their APK and nothing on the console. The pill
still says "On" because the FCM subscription registered successfully.

**Fix path:** on server start (once), if any `fcm` row exists in
`push_subscriptions` but `FCM_SERVICE_ACCOUNT_JSON` is missing, log a
prominent WARN. Also make the `push/test` endpoint return a clear message
for this state (right now it returns
`"FCM not configured on server (FCM_SERVICE_ACCOUNT_JSON missing)"` — good
but the pill doesn't surface it).

### A3 · P1 · `notifyAgentsOfHandoff` fans out to every agent, not to those with permission for this conversation
**File:** [src/push.js:91](../src/push.js) — `select * from push_subscriptions`
with no `where agent_email in (…)` filter.

There is no agent-conversation assignment model, so every subscribed agent
gets every handoff notification. Fine for a one-client single-team setup;
becomes noisy the moment there are two teams.

**Fix path:** either add a `select from push_subscriptions where
agent_email in (select email from agents where active)` for correctness, or
document that this is intentionally global.

### A4 · P2 · `pushHandoff` fires for zero-body text messages
**File:** [src/handlers/message.js](../src/handlers/message.js) inbound-while-
human branch. The condition `message.text?.body || message.type !== 'text'`
is `true` for every real WhatsApp message but silently skips a malformed
webhook where `type === 'text'` and body is empty. Not a bug, but worth
inverting for readability: `if (!(text is empty)) push()`.

### A5 · P2 · `console.error` in `src/push.js:37` bypasses Pino
Standard pattern in this repo is `log.error(...)` via Fastify's logger. This
one line prints to stderr without correlation.

### A6 · P2 · Batcher singleton captures first config
**File:** [src/handlers/message.js:57](../src/handlers/message.js). Module-
level `let batcher = null;` means the second call with a different config is
silently ignored. Fine in production (config is static) but a footgun if a
future test swaps timings.

### A7 · P1 · Duplicate migration name still applied
**File:** [src/db/migrations/](../src/db/migrations/). The
`schema_migrations` table has both `011_handoff_pending_and_learning.sql` and
`011_handoff_pending.sql` applied. Only the second one exists on disk. On a
fresh install, only the second runs — so the first was pruned but its DB row
lingers. Harmless today; misleading during forensic debug.

**Fix path:** delete the stale row from the DB, or leave a note in a
`docs/migrations-history.md`.

## B. Service worker and web push

### B1 · P0 · Icon casing mismatch (already caught by user in latest edit but not verified)
**File:** [web/public/service-worker.js:58-59](../web/public/service-worker.js)
now references `/Icon192.png`. `web/public/` has `Icon192.png` and
`Icon512.png` (capitalised). The manifest is also correctly capitalised. On
Linux (case-sensitive), the earlier lowercase `/icon-192.png` would 404;
the current capital form is correct. Verify one more time after any icon
regenerate step.

### B2 · P1 · Service worker version bump requires manual code edit
**File:** [web/public/service-worker.js:5](../web/public/service-worker.js)
`const VERSION = 'sw-2026-08-30-3';`. Every release you must bump this
string by hand, or browsers cache the old SW and clients silently run old
notification logic. This burned us once already.

**Fix path:** compute the version from `__BUILD_INFO__.gitSha` at build
time. Since the SW is served from `public/` unhashed, wire a Vite plugin or
a post-build script that string-replaces `sw-DEV` with `sw-<sha>`.

### B3 · P1 · `viewingConversationId` suppression can miss cross-device intent
**File:** [web/public/service-worker.js](../web/public/service-worker.js)
`push` handler. The suppression only fires when *this device's* SW has
`viewingConversationId === payload.conversationId` **and** at least one
client is focused. Correct in isolation, but two edge cases:

1. The agent has the same chat open on desktop and phone. The desktop SW
   fires no notification (they're looking). The phone SW also fires no
   notification if the phone was foregrounded (rare — usually only one
   device is active). But if the phone tab is *stale* and viewingConvo is
   still the same chat while the phone screen is off, the phone won't ping
   — even though the agent isn't looking at the phone.
2. Toggling browser tabs quickly can leave `viewingConversationId` stale
   for a few hundred ms.

Acceptable trade-off. Document, don't change.

### B4 · P1 · `notificationclick` handler doesn't focus the tab
**File:** [web/public/service-worker.js:70](../web/public/service-worker.js).
Per product spec ("clicking dismisses"), the click handler only closes the
notification. But on Android APK, tapping a notification while the app is
backgrounded currently does nothing at all — not even bringing the app to
front. Users expect at least the app to open.

**Fix path:** add `event.waitUntil(clients.matchAll(...).then((cs) => {
if (cs[0]) return cs[0].focus(); return clients.openWindow('/'); }))`. Do
not deep-link into the chat (per spec), just focus the shell.

### B5 · P2 · Push tag reuses `chat-<id>` — good in one direction, wrong in another
**File:** [src/push.js:104](../src/push.js). Because the tag is per-chat,
a burst of messages collapses to one line in the tray. Good. But if a
handoff push and an inbound-message push land back-to-back for the same
chat, the handoff notification is silently replaced by the inbound preview
— which is a less important signal ("sent a message" > "needs a person").

**Fix path:** use different tags for `handoff-<id>` vs `inbound-<id>`, or
keep the shared tag but always prefix the body with the last important
event.

### B6 · P2 · No listener for token refresh
**File:** [web/src/push.js](../web/src/push.js) native path. FCM tokens can
rotate silently (uninstall+reinstall, storage wipe, etc.). We register on
launch via `autoRegisterIfNative`, which is enough, but we don't listen for
the token-refresh event so a rotation mid-session goes unnoticed until
next app open.

**Fix path:** `PushNotifications.addListener('registration', ...)` is set
in `_doNativeRegistration`. Confirm it stays registered for the app's
lifetime — the current code calls `removeAllListeners()` at the start of
each registration, which will drop the previous listener.

## C. Frontend UI / UX

### C1 · P0 · Push pill absent from the mobile top bar
**File:** [web/src/App.jsx:314-332](../web/src/App.jsx) mobile top bar +
[web/src/components/layout/Sidebar.jsx:179](../web/src/components/layout/Sidebar.jsx).

The `PushPill` lives in the sidebar footer. On desktop, the sidebar is
always visible → OK. On mobile, the sidebar is a drawer that only appears
after tapping the hamburger → the agent cannot see whether push is on
without opening the drawer. The punch list spec (§2.2) called for the pill
to appear on the right of the mobile top bar, left of the hamburger. Not
implemented on mobile.

**Fix path:** render `PushPill` inline in the mobile top bar between the
brand title and the hamburger. Give it a tighter variant (icon-only, no
"On/Off" label) so it doesn't push the brand.

### C2 · P0 · The "Turn on notifications" banner has no dismiss persistence when the user is on Denied
**File:** [web/src/App.jsx:167-170](../web/src/App.jsx).
`dismissBanner()` writes `wa_push_state = 'dismissed'` and the banner is
gated on `pushState === 'default'`. Good. But `resolveInitialPushState`
reads `Notification.permission` first — if it's `denied`, we skip localStorage
entirely and return `'denied'`. So the banner correctly hides in that case.

The subtle bug is different: if the OS silently keeps `Notification.permission
= 'default'` after the user Dismissed the browser prompt with the ✕, the
banner shows on next reload because localStorage was never written
(dismiss was for the *banner*, not for the *prompt*). Confirmed by reading
the code: `turnOnPush` only writes state on completion, not on cancel.

**Fix path:** when `Notification.requestPermission()` resolves with
`'default'` (user closed the prompt), treat that as `'dismissed'` too.

### C3 · P1 · Thread header still overflows for very long names + assignee
**File:** [web/src/Console.jsx:734-746](../web/src/Console.jsx). The wa_id
and assignee row has `min-w-0` and `truncate` (fixed earlier) but
`EditableName` uses `inline-flex` which sizes to content. With a very long
alias ("Rajesh Bharat Somendra Kumar…") the pencil button sits *after* the
truncated text but the `inline-flex` container can still exceed the parent
because inline-flex only respects `max-w-full` when a parent constrains it
in the block-flow direction; the row's `flex-1 min-w-0` does that, so it
should work — but the pencil button lacks `flex-shrink-0`, so a name at
exactly the boundary can push it off-screen.

**Fix path:** in [EditableName](../web/src/Console.jsx#L575), change the
`<span>` to `flex` (not `inline-flex`) and add `flex-shrink-0` to the
`<button>` and `<Pencil>`.

### C4 · P1 · Mobile top bar height uses 64px, but banner adds another ~40px
**File:** [web/src/App.jsx:314-332](../web/src/App.jsx). The mobile top bar
is 64 + safe-area. The banner adds ~40. That's ≈ 104px before the chat list
starts — more than the punch-list budget of ≤ 116px, but still eating
enough of a 667-tall iPhone SE that the visible chat rows drop from ~7 to
~5. Not broken, but noticeably tight.

**Fix path:** either merge the banner into the top bar visually (spec §2.3,
option 1) or reduce top bar to 56px on mobile.

### C5 · P1 · `text-2xl` brand name in the mobile top bar competes with everything
**File:** [web/src/App.jsx:324](../web/src/App.jsx). `text-2xl` (24px) is
oversized for the mobile top bar and gets truncated even at 375px if the
brand is longer than ~10 characters. It also fights the thread header's
`text-sm md:text-base` name treatment when navigating between screens.

**Fix path:** `text-lg` on mobile top bar for balance with the punch list's
type scale.

### C6 · P1 · Toast width `w-[300px]` overflows on very narrow phones with brand context
**File:** [web/src/components/ui/Toast.jsx:78-83](../web/src/components/ui/Toast.jsx).
Fixed width 300px + `max-w-[calc(100vw-2rem)]` — reasonable. But on 320px
screens (iPhone SE 1st gen still exists) it hits the cap and the message
gets very tight; also the position `top: 72px` covers content, and the
notification stack doesn't check whether the top bar is currently visible
(admin views have no mobile top bar, so 72px of empty space above the toast).

**Fix path:** make the top offset conditional or read the top-bar height
via a CSS variable set by App.jsx.

### C7 · P1 · Toast duration `1000ms` is too short to read a real message
**File:** [web/src/components/ui/Toast.jsx:60](../web/src/components/ui/Toast.jsx).
User set 1 second globally. That's fine for "Saved" but too short for
"Test sent to 2 devices" or a handoff warning that also should give the
agent a moment to click the action button.

**Fix path:** default to 2500ms; keep 1000ms for pure success (`success()`)
via per-type default.

### C8 · P1 · Composer library button hidden on `<sm` breaks discovery of media library
**File:** [web/src/Console.jsx:849](../web/src/Console.jsx). We
`hidden sm:flex` the Library button on <640px. The Paperclip covers direct
attachment, but there is no other way to open the media library from mobile.

**Fix path:** either put the library into an overflow menu (⋯) alongside
the template picker, or leave both visible and shrink the composer input.

### C9 · P1 · `<Ticks>` uses red for `read`
**File:** [web/src/Console.jsx:194-195](../web/src/Console.jsx). User's
choice, keep — but red on a dark bubble reads as an error state. If this
is intentional (brand accent = red for the client?), fine; if it's just a
placeholder, swap to WhatsApp blue (`text-sky-400`) or the accent green.

### C10 · P1 · Bubble text-align + tick alignment cause overlap on very short bubbles
**File:** [web/src/Console.jsx:801-807](../web/src/Console.jsx). Punch-list
item §3.3 flagged this. Short outbound bubbles ("ok", "yes") let the tick
strip visually overlap the body. Give outbound bubbles `pr-14` and shift
the tick strip absolutely, or add a minimum bubble width of ~64px.

### C11 · P1 · Chat list "unread badge" is green but pending indicator is amber
**File:** [web/src/Console.jsx:527-540](../web/src/Console.jsx). Two different
colours for two overlapping signals (both mean "attention needed"). Consider
unifying — use amber for both, and let the size distinguish (dot vs.
numbered pill).

### C12 · P2 · Search bar clear (✕) is a raw text "×" instead of a lucide `<X/>`
**File:** [web/src/Console.jsx](../web/src/Console.jsx) list search. The
Unicode multiplication sign renders at slightly different sizes across
platforms. Use the lucide icon for consistency.

### C13 · P2 · `EditableName` pencil is always visible; punch list §2 wanted it as a hover-only affordance
**File:** [web/src/Console.jsx:577-585](../web/src/Console.jsx). The
`opacity-60 hover:opacity-100 transition-opacity` on the button is a nice
touch, but pointer-hover doesn't exist on mobile so the button just sits
at 60% opacity permanently on phones. Consider `md:opacity-60` so the
pencil is fully visible on touch devices.

### C14 · P2 · Focus rings missing across most `<button>`s
**File:** [web/src/styles.css](../web/src/styles.css). Punch-list §4.5
called for `:focus-visible` rings. Not implemented. Not a blocker for a
one-client tool, but keyboard-only agents (screen readers) can't tell
where they are.

## F. Capacitor APK + FCM

### F1 · P0 · `capacitor.config.json` points at a free ngrok URL
**File:** [capacitor.config.json](../capacitor.config.json). `server.url =
"https://expiring-duration-parting.ngrok-free.dev"`. Free ngrok tunnels
change on every restart. When the URL changes, every installed APK on
every phone is instantly broken — the WebView loads a dead host.

**Fix path:** either reserve a static domain on ngrok, or deploy the
backend behind a real domain (DigitalOcean droplet + Caddy →
`console.advoice.in`).

### F2 · P0 · No `google-services.json` in `android/app/` — FCM tokens register but no push is deliverable
Confirmed by A2 above. The pill says "On" and `push_subscriptions` fills
up with `transport = 'fcm'` rows, but zero notifications reach the phone
from the APK.

**Fix path:** Firebase console → add Android app with
`com.thetwocubes.console` → download `google-services.json` → drop into
`android/app/` → set `FCM_SERVICE_ACCOUNT_JSON` env in the backend → restart.

### F3 · P1 · APK version code never bumps
**File:** [scripts/build-apk.sh](../scripts/build-apk.sh). Every APK built
has the same `versionCode`. Android treats it as no-op update — the client
uninstalls the old one to install the new. Add a step that reads
`package.json` version and patches `android/app/build.gradle`.

### F4 · P1 · Build script doesn't sync ngrok URL change into the APK
**File:** [scripts/build-apk.sh](../scripts/build-apk.sh). If the ngrok
URL changes and you forget to update `capacitor.config.json` before
running `npm run apk`, the built APK bakes the stale URL. Add a hint at
the top: `if server.url contains "ngrok"`, warn.

### F5 · P2 · `@capacitor/assets` was installed as devDependency but never wired
**File:** [package.json:34](../package.json). Presumably added to generate
adaptive-icon variants. If unused, remove; if intended, add a
`build/generate-assets.sh` that runs `npx capacitor-assets generate`.
